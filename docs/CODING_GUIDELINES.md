# 编码指导

本项目的编码风格遵循 Karpathy 风格的工程原则：先做简单、可运行、可理解的系统，再在真实需求推动下增加复杂度。目标不是写“看起来高级”的代码，而是写能长期维护、能测试、能复盘、能安全进化的代码。

## 核心原则

## 1. 先跑通最小闭环

任何新能力都应先形成最小可运行路径：

```text
输入 -> 处理 -> 输出 -> 验证
```

在没有跑通闭环之前，不要先堆复杂抽象、框架、插件系统或多 Agent 编排。

## 2. 简单优先

- 优先使用普通函数、清晰的数据结构和显式流程。
- 避免为了“未来可能需要”提前设计复杂扩展点。
- 避免深继承、隐式注册、全局魔法和难追踪副作用。
- 抽象必须由真实重复和真实复杂度驱动。

## 3. 可读性优先于聪明写法

代码应让下一位维护者快速理解：

- 这个模块负责什么。
- 输入和输出是什么。
- 哪些状态会变化。
- 错误如何传播。
- 如何验证它是对的。

如果一段代码需要大量解释才能看懂，优先重写结构，而不是补长注释。

## 4. 显式数据和状态

投资 Agent 的风险来自不可见状态和不可复盘决策。涉及以下内容时必须显式建模：

- 投资假设。
- 交易计划。
- 告警。
- 执行记录。
- 复盘结果。
- skill/config 版本。
- 评估指标。
- 晋升和回滚门禁。

不要把关键状态藏在 prompt、临时内存、日志文本或不可结构化的自然语言里。

## 5. Baseline 先行

对复杂能力先建立 baseline：

- 先用规则或简单模型跑通。
- 再加入 Agent 推理。
- 再加入多 Agent 协作。
- 再加入自我进化。

没有 baseline，就无法判断复杂版本是否真的更好。

## 6. 测试和评估先于扩展

每个重要能力至少要有一种验证方式：

- 确定性代码使用单元测试。
- 多模块流程使用集成测试。
- 投资策略使用回测。
- Agent 行为使用 eval。
- 候选 skill 使用 shadow live。
- 账户风险变化使用人工审批和回滚规则。

不能验证的复杂逻辑，不应进入高风险路径。

## 7. 日志和复盘是功能的一部分

Agent 不是只给答案，还必须留下证据。涉及投资建议、告警、组合、策略或 skill 进化时，必须能回答：

- 当时看到了什么数据？
- Agent 做了什么判断？
- 用户是否采纳？
- 结果如何？
- 失败模式是什么？
- 是否产生候选改进？

这些信息应进入 ledger、review 或 eval 产物，而不是只留在聊天记录里。

## 8. 小步提交

优先小步、可回滚的变更：

- 一次提交解决一个清晰问题。
- 文档、测试和代码一起演进。
- 不夹带无关重构。
- 不为了美观大规模改动历史产物。

## 9. 不确定时先降级

遇到不确定设计时，优先选择更简单、更可控的路径：

- 先本地离线。
- 再模拟环境。
- 再 shadow live。
- 最后才考虑生产或实盘。

任何实盘、账户风险、自动晋升相关能力，都必须默认关闭并需要人工门禁。

## 10. 注释规则

- 代码注释和 docstring 必须使用中文。
- 注释解释“为什么”和“风险”，不要重复“代码做了什么”。
- 第三方 API 名称、协议字段、错误原文和命令输出可以保留英文。
- 如果注释变得很长，优先考虑拆函数或写设计文档。

## 本项目的默认判断

当简单方案和复杂方案都可行时，默认选择简单方案。只有当复杂方案能明显提升可复盘性、可测试性、可靠性或投资风险控制时，才引入复杂度。
