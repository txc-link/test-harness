# Figma 原型快速开发验证流程

本文定义投资 Agent Harness 如何接入 Figma 插件，把“需求构思 -> 原型 -> 实现 -> 浏览器验证 -> 复盘”纳入正式工程闭环。

## 结论

当前 Codex 环境已经具备 Figma 插件能力。自本文档起，Figma 原型验证被纳入项目级 Harness 主流程：凡是涉及前端控制台、盯盘面板、告警中心、复盘页面、策略分析页面和审批队列的需求，都必须先走原型验证，再回写需求并排期开发。

## 适用范围

需要走 Figma 原型验证的场景：

- 新增投资 Agent 控制台页面。
- 新增盯盘、告警、分析、复盘、回测或收益归因视图。
- 调整关键交易风险、人工审批或 skill 晋升界面。
- 需要和用户确认信息架构、操作路径或可视化密度的复杂功能。

可以跳过 Figma 的场景：

- 纯 CLI、schema、CI、测试或后端内部逻辑。
- 小范围文案、链接或非交互文档调整。
- 已有界面的窄范围 bug 修复。

## 标准流程

```text
需求文档
  -> 信息架构草图
  -> Figma 原型
  -> 人工确认
  -> 需求回写
  -> 路线图调整
  -> Sprint 排期
  -> 前端实现
  -> 浏览器截图验证
  -> 测试与 CI
  -> 复盘记录
```

## Harness 产物要求

每个需要 Figma 的需求至少保留以下证据：

- `docs/requirements/REQ-*.yaml`：说明原型要验证的用户问题。
- `docs/rfc/*.md`：记录信息架构、页面状态、关键交互和数据依赖。
- Figma 链接或截图：放入 RFC、PRD 或 review 文档。
- `docs/test-plans/*.md`：写明浏览器验证路径。
- `docs/reviews/*.md`：记录原型评审结论和实现偏差。
- `docs/roadmap/*.yaml` 和 `docs/sprints/*.yaml`：体现原型确认后的拆解和排期。

## 需求回写规则

人工确认原型后，必须重新梳理需求，再进入开发：

- 如果原型改变信息架构，更新 PRD 或 RFC。
- 如果原型改变范围，更新 `docs/requirements/REQ-*.yaml` 的 scope、non_goals 或 acceptance_criteria。
- 如果原型改变优先级，更新 roadmap 和 sprint。
- 如果原型暴露风险，更新风险登记、测试计划或质量门禁。
- 未完成原型确认的界面类任务不得标记为 ready，也不得进入大规模实现。

## 插件使用原则

- 生成新界面时，先用 Figma 插件产出可讨论的原型，不直接进入大规模编码。
- 从 Figma 实现代码时，必须结合本仓库技术栈和现有样式，不盲目复制生成代码。
- 浏览器验证必须检查布局、文案、状态覆盖、移动端表现和关键交互。
- 投资风险相关页面必须展示数据来源、更新时间、风险提示和审批状态。

## 与面板的关系

Harness 面板负责显示工程状态，Figma 负责降低前端需求的不确定性。后续可以把 Figma 原型链接写入 `status.json`，让每个前端任务在面板卡片中直接展示：

- 原型链接。
- 原型评审状态。
- 截图验证状态。
- 实现偏差说明。

## 下一步增强

- 在 ticket schema 中增加 `prototype_url` 和 `prototype_review_status`。
- 在 dashboard 中展示每个前端任务的 Figma 原型链接。
- 在 CI 中保存 Playwright 截图作为面板附件。
- 对关键页面建立“原型截图 vs 实现截图”的人工验收清单。
